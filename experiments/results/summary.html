gorilla-tsc: overnight research results

Two questions about the compression library. Every number below was measured on this machine and read from the JSON results files. Every codec reported was decoded and compared bit-for-bit (Q2: 40/40 methods verified, Q1: all profiles).

1. One codec for everything?

Yes for the family, no for the parameters

decimal (floats) and delta (integers) match auto on almost every dataset. Restricting auto to {decimal, xor} loses nothing on any of the 25 datasets. The cost is in the parameter search inside decimal. Locking the parameters learned from the first 10k values encodes 9× faster with a median ratio change of +0.0%.

2. Other strategies

-15% (time series), -13% (other)

Five new per-block candidates (dictionary, repeat cache, decimal split, adaptive bit split, LPC) together shrink output by about 14% while keeping 1000-value random access, and beat xz and pcodec on time series. The biggest single win is the decimal split on float32-derived data (Basel-temp 25.6 → 11.9 bits/value).

1. Is there one compression that does well everywhere? Can we sample instead of trying everything?

Method: every mode was run on every block of 1000 values of 25 datasets: 22 Elf benchmark sets (~100k values each), the full 5M-value Chimp stock series, and two timestamp series. Each strategy was then scored against auto, which tries every mode on every block. The harness's best-of sum equals the library's own auto output exactly.

  • Mode level: yes. decimal wins nearly every float block and delta every integer block. The only exceptions are high-precision "real doubles" (POI-lon, Air-sensor), where xor wins. Restricting auto to two candidates ({decimal, xor} or {delta, dod}) gives the same size as all six on every dataset.
  • Sampling the first n values to pick the mode works. 1000 values picked the best fixed mode on all 25 datasets. Probing only the head of each block is worse (City-temp, PM10, Food-price) and barely faster. Don't do that.
  • But mode locking alone barely speeds things up (21 vs 18 MB/s), because decimal itself searches exponents, difference orders and coders per block. The real win is locking those as well: a production profile learned once from a sample.
  • Sample size matters. Learned from only 1000 values, the profile can choose too few decimal places, and later values become 64-bit exceptions (Stocks-UK goes from 4.8 to 25.4 bits/value). Learning from 10k values plus an exception guard fixes this: a block that leaves more than 1% exceptions re-picks its exponent.
  • Re-learning when a block suddenly gets bigger, or every 16/64 blocks from recent data, made things worse: it overfits single blocks. One lock learned from a decent sample was the most robust.

Food-price is the one dataset where locking clearly loses: its blocks need different exponents (k = 1–4). A per-block exponent from a one-pass "covering" histogram brought it to about 11.5 (see q1.json). Recovering the rest needs the full per-block search.

Answer: keep auto as the exploration tool, which matches your intuition. Add a Profile type (mode + exponent + order + coder) that can be learned from a sample, stored, and passed to an encoder for production use. Expect about 10× faster encoding at about the same ratio. Two free library fixes also turned up: (1) each block's first value is stored as a raw 64-bit word, which costs about 0.04 bits/value; a length prefix fixes it. (2) On POI-lon auto spends 66 bits/value, more than raw, so a verbatim fallback is needed.

What each strategy showed

  • Decimal split (best new idea): many float series are decimal readings plus a constant float32 offset (Basel-temp 1.9005287, 1.6105287, …). Splitting the scaled integer into a reading and a tiny remainder halves Basel-temp, beating pcodec and xz. Food-price −15%, Bird-migration −10%.
  • Dictionary: helps even on mostly-distinct blocks (a sorted dictionary has tiny deltas). SSD-bench −46%, Basel-wind −25%.
  • Adaptive bit split (ALP-RD style): fixes the "real doubles" where auto spends 62–66 bits/value. POI −13 to −16%.
  • Not worth it: LPC on floats (−0.3%), trained priors (≤ −1.4%), carrying the coder state across blocks (−1.5 to −3%, at the cost of random access), and bigger blocks for auto alone.
  • Where xz and pcodec still win: exact repeats across blocks (in POI-lat, 33% of values repeat an earlier value, but only 1% within their block). A chunk-level shared dictionary is the biggest remaining gain on non-time-series data (not yet measured).
  • Cost: auto+all encodes at about 1 MB/s because it tries 11 candidates per block. That is exactly what question 1's profile lock fixes.

Library inputs from questions 1 and 2

  1. Add Profile learning and locked encoding (question 1). It's what makes the slow candidates affordable.
  2. Add per-block candidates: decimal split, dictionary, adaptive bit split (the 3-bit selector has two free codes; going to 4 bits costs about 0.001 bits/value).
  3. Store the first value with a length prefix, and add a verbatim fallback.
  4. Later: a chunk-level shared dictionary (format change) for cross-block repeats.

Method, caveats, reproduce

  • Datasets: 22 Elf sets (about 100k-value subsets of the sets in the Elf and ALP papers, so only roughly comparable with their full-set numbers), Chimp Stocks-Germany (5M), timestamps. Fetch with scripts/fetch-bench-data.sh. The harness reproduces Gorilla's published bits/value to within 0.07.
  • Machine: one core of an i7-8700K. Q1 timing was run sequentially on an idle machine. Q2 was re-run on an idle machine.
  • Spot checks by hand: system xz/zstd on raw f64 bytes match Q2's baselines.
  • Experiment codecs aren't hardened against corrupt input. They're research code, not library code.
  • Reproduce: experiments/q1-mode-selection: cargo run --release and cargo run --release -- --timing. experiments/q2-strategies: cargo run --release -- --jobs 1. This page: python3 experiments/results/make_summary.py.
  • Write-ups: experiments/results/q2-findings.md. Raw data: q1.json, q1-timing.json, q2.json.
